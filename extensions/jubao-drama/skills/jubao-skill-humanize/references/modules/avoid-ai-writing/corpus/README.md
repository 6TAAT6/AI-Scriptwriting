# 人工对照语料库

本仓库对误报（false positive）做出了若干断言。分级体系的存在是"为了减少对那些单独出现没问题、但在簇集出现时才可疑的词的误报。"容忍矩阵（tolerance matrix）会按语域（register）放宽规则。`SKILL.md` 开篇即指出，这些模式（pattern）是"信号，而非证据。"

但上述断言此前从未被实测过。本语料库就是用来完成这一测量的。

## 设计思路

这里的每一篇文档都是由人写的。因此检测器对它发出的每一次命中，从构造上就是一次误报。这里没有标注步骤，没有评判员，也没有模型在环：真值（ground truth）就是来源（provenance）本身。

**本语料库只存哈希。** `manifest.json` 记录每篇文档是什么、来自何处、采用何种许可证、属于哪个语域，以及被测量时那段精确文本的 sha256。文本本身从不提交进仓库。公有领域（public-domain）来源会被抓取到一个被 gitignore 的 `cache/` 目录；私有内容则留在它原本所在的位置，只贡献它的哈希。这样既保持了测量的可审查性，又不必重新发布任何人的文字。这一做法借鉴自 `devswha/patina`，后者在其韩语人工对照（human control）中使用了同样的模式。

```bash
node scripts/corpus.js list      # 查看 manifest 中的内容
node scripts/corpus.js fetch     # 填充 cache/
node scripts/corpus.js verify    # 检查 cache 是否仍与记录的哈希匹配
node scripts/fp-measure.js       # 执行测量
```

`verify` 在哈希不匹配时会大声报错，而不是悄悄重新记录。某个来源如果在我们之下被改动，就会使它所支撑的那项测量失效，而这应当成为一个需要争论的问题，而不是一次悄无声息的更新。

## 语域（Register）是分析的基本单位

它不是一个为了方便而贴的标签。Patina 的韩语人工对照试点在单一语言内测得误报率，从聊天式更新的 4.0% 一直跨度到技术操作类散文的 34.0%。如果只用一个汇总率，那这个率几乎完全会被最差的那个语域所决定，从而把这个发现本身给掩盖掉。

本仓库的容忍矩阵本来就断言了各语域之间存在差异。语域分桶（register buckets）正是让这一断言能被检验、而不是被默认假定下来的关键。

## 当前内容

两个来源，出于不同理由被选中。

**九篇公有领域作品，时间跨度 1788 至 1907 年**，每篇切成 6,000 词。它们的来源无可争辩：1859 年写下的任何东西都不是机器生成的。但这也是它们的局限，而且这一局限很严重。没有人会把本工具用在《瓦尔登湖》（*Walden*）上。单凭这一支，它只能证明检测器不会对正式的英文散文乱开火。

**由本仓库维护者所写的二十五篇博客文章，时间 2019 年至 2022 年 12 月**，读取自**"Web 版的古登堡计划"**：即 2023 年之前抓取的 `web.archive.org` 存档快照。这些文章写于 ChatGPT 之前，所处的语域也正是本工具真正被指向的那一语域，而且作者身份毫无争议。这一支产出了有用的发现。

从存档而非线上站点读取它们，是刻意为之。线上站点此后被重建过，文章也被修订过；中位存档快照与其当前发布版本之间仅有 **0.92 的相似度**，二十五篇中有五篇相似度低于 0.90。拿"他 2023 年之前的写作"去对照 2025 年修订过的页面，量到的是错的东西。

解析这些 URL 并不是简单地换一个域名的事。老站点使用的是压缩式 slug（`beveragetax`、`challengerfunnel`、`emailmarketing`），与当前的 URL 并不匹配，因此候选目标是先按 slug 相似度找出，然后再**通过内容来核实**：只有当某存档页面提取出的文本与当前版本之间的 Jaccard 相似度至少达到 0.45 时，它才会被接受。真正的匹配落在 0.76 到 0.98 之间。有四个 slug 猜测的得分低于 0.17，被这一检查所拒绝，而不是被悄悄接受——这正是该检查存在的全部理由。

被排除的内容，全部记录在案，而不是被悄悄丢弃：

- **同一站点上的两篇客座文章**，作者为 Adam Noble 和 Steve Fawthrop，是通过署名行（byline）发现的。它们是人写的，因此本不会污染误报率，但把它们归到错误的作者名下会。
- **三篇带有"从 2025 年回望"回顾段落的文章**，这些段落是发表多年之后才加进去的。它们 LLM 之前的来源链条已经断了。这是通过阅读得分最差的段落发现的，而不是靠工具中的任何检查发现的。
- **九篇没有可验证的 2023 年前存档快照的文章。** 其中五篇根本没有存档快照；另外四篇的候选 slug 没能通过内容检查。它们被排除在外，而不是用其当前站点的文本纳入——因为一个来源规则会为图方便而变通的语料库，就不配叫来源规则。

## 机器这一半

两个数据集，之所以被选中，是因为它们在相反的方向上失败，而这种差异最终恰恰成了核心发现。

**RAID**（Dugan et al. 2024，MIT）——横跨 8 个英文领域、来自 11 个模型族，按字节范围从一个 11.8 GB 的 CSV 中采样。它的任务是域内续写（in-domain continuation）：续写完这篇新闻报道、写出这份菜谱、起草这段摘要。它还自带了人类基线（human baseline）行，这里作为独立的人工对照保留。

**HC3**（Guo et al. 2023，CC-BY-SA-4.0）——即 Human ChatGPT Comparison Corpus（人 ChatGPT 对比语料库）。每条记录都是同一个问题，既有一个人类回答也有一个 ChatGPT 回答，因此这种对比是**按主题配对的（paired on topic）**，这是在不在此地生成任何内容的前提下能拿到的最强实验设计。这属于助手语域（assistant register）：对冲措辞（hedging）、 dutiful 式的"两面都要照顾到"的框架、"it is important to note"（"需要注意的是"）。

这两个数据集都不是由与本仓库数字有任何利益关系的人生成的。这一点比听起来更重要：由评估检测器的人自己生成的语料库，量到的是他的提示词（prompting）水平，与量到检测器本身一样多。

**制约下文每一个数字的那条告诫。** HC3 是 2022 年 12 月的 ChatGPT，正好是这一类工具被造出来要捕捉其习性的那个时代；而 RAID 是 2024 年的。此处测得的真正例率（true-positive rate）是对当前模型性能的一个**上界（upper bound）**，而不是对它的估计。这里没有任何东西见过 2026 年的模型。

## 结果（v3.22.0，2026-07-31）

875 个人类段落，779 个机器段落。

| 阈值 | FPR (95% CI) | TPR (95% CI) |
|---|---|---|
| score >= 3 | 16.6% (14.3–19.2) | 16.3% (13.9–19.1) |
| score >= 5 | 4.2% (3.1–5.8) | 7.2% (5.6–9.2) |
| score >= 10 | 0.5% (0.2–1.2) | 0.1% (0.0–0.7) |
| score >= 15 | 0.0% (0.0–0.4) | 0.0% (0.0–0.5) |
| score >= 25 | 0.0% (0.0–0.4) | 0.0% (0.0–0.5) |

**ROC-AUC，段落级：汇总 0.501。** 按来源分：HC3 0.554，RAID 0.451。在文档级（这更接近真实使用场景）：**汇总 0.623，HC3 0.654，RAID 0.599。**

直白地读：**这个综合分数无法可靠地把机器文本与人类文本分开。** 0.5 是抛硬币。0.65 是弱。在这条标尺上，没有任何一个阈值能在可容忍的误报率下买到一个有用的真正例率，而能找到的最佳工作点——文档分数 score >= 3——要付出 12.8% 的误报代价才能捕获 27.7% 的机器文本。

### 三项发现，按其应改变路线图（roadmap）的程度排序

**1. 0–100 这条标尺只用了其范围的大约十分之一。** 无论哪一类的任何段落，得分都没超过 11。每一个 15 及以上的阈值在两侧都报出 0.0%，而 `SKILL.md` 自己的标签分带（label band）把一切 15 及以下的都归入"Minimal AI signals"（极弱 AI 信号）。所以在实际使用中，每一个普通段落都会被标为 Minimal，而不管它是谁写的。原因是机械性的：各类别权重在 2–12 之间，而 `rawScore` 会被 `max(1, log2(words / 50))` 除，所以一个 200 词的段落的总分会被砍掉一半。这是一个校准缺陷（calibration defect），而不是检测失败，而且它是本页上最可修复的东西。

**2. 存在的信号是结构性的，而不是词汇性的。** 各类别在文档级的触发率：

| 类别 | 人类 | 机器 | 提升（Lift） |
|---|---:|---:|---:|
| `uniformity` | 2.1% | **25.1%** | **11.7x** |
| `filler` | 2.4% | 8.3% | 3.4x |
| `low-ttr` | 6.4% | 9.8% | 1.5x |
| `chatbot` | 0.0% | 1.1% | 仅机器 |
| `fnword-trigram-entropy` | 0.0% | 1.5% | 仅机器 |
| `hedge-stack` | 0.0% | 1.0% | 仅机器 |
| `tier1` | 8.0% | 7.4% | **0.9x** |
| `em-dash` | 9.9% | 1.9% | **0.2x** |

节奏一致性（rhythm uniformity）是整个引擎中唯一最佳的判别器（discriminator），优势大出一个数量级。那张 112 条的词汇表——也就是本 README 一开场就摆在最前面、投入工作量最多的那个东西——的提升是 **0.9**。它在人类写作上的触发频率反而比在机器写作上*略高一些*。

这正是 `NulightJens/humanizer-stack` 借助 StoryScope 所论证的（仅靠篇章特征就能达到 93.2% 的 F1，而专业的表层改写只让检测分数移动了 1.6 个点），也是 `harshaneel/humanize` 独立论证过的东西。在本引擎、在本语料上测出来，他们看起来是对的。

**3. `em-dash`（破折号）是反的。** 它在 9.9% 的人类文档和 1.9% 的机器文档上触发——提升为 0.2。在本语料上，一个破折号是文本*由人类所写*的证据。这一点在两支数据上都成立，而且不是转录伪影（transcription artifact）：维护者自己 2019–2022 年的文章里到处都是破折号，而 RAID 和 HC3 的生成内容里则没有。作为*写作*建议，这条规则本身没错，维护者此后也有意识地削减了破折号的使用。但作为一种作者身份信号，就本证据而言，它的指向是反的。

### 这些发现并不授权做什么

它并不授权说"这个检测器不工作"。它量的是一件事：综合分数在两个 2022–2024 年语料上把两个带标签的类别分开的能力如何。本 skill 被文档化为一个写作质量工具，而上述任何内容都不涉及它的编辑是否真的改善了文字。

它也并不授权重写模式清单（pattern list）。一个接近 1.0 的提升只是说，某个类别在*这些*语料上不能把*这两个*类别分开；`delve` 仍然值得替换。

它真正授权的，是一次重点的转移：那些结构性和计量文体学（stylometric）检测器承担了全部的判别负荷，而它们恰恰是整个引擎里开发得最不充分的部分。

## 这些数字量不到的东西

**没有当前模型。** 每一个机器单元都早于 2025 年。这一品类的全部前提就是模型习性会发生迁移；这些数字无法对语料收集之后发布的模型发表任何意见。

**只有一个助手语域的模型族。** HC3 只有 ChatGPT。RAID 又加了十个模型族，但任务形态不同。这里没有任何东西是现代的、经过指令微调（instruction-tuned）的模型在写一篇 LinkedIn 帖子，而那才是真实的用例。

**没有本地生成——是故意的。** 在此地生成正例，会让这些数字变成对提示词水平的测量，与对检测器本身的测量一样多，而那些提示词不可避免地会由了解模式清单的人来写。

**没有任何声明达到了发布标准（release-ready）。** 借鉴 patina 的公开声明门槛（public-claim gate）：在本语料的任何数字进入 README、发布说明或社交媒体帖子之前，每一个声明单元格都必须满足 n >= 100、覆盖一个以上人们今天真正在写作的语域，并附带置信区间。当前这一轮满足了区间和 n 这两项，但在语域这项上彻底不达标。

## 如何添加内容

公有领域或宽松许可证的来源，且可通过 URL 抓取：

```jsonc
{
  "id": "short-slug",
  "title": "...", "author": "...", "year": 1900,
  "register": "blog",              // see REGISTERS in scripts/corpus.js
  "authorship": "human-pre-llm",
  "source": { "type": "url", "url": "https://…", "license": "public-domain", "gutenberg": true },
  "slice": { "after": "literal marker string", "maxWords": 6000 }
}
```

然后 `node scripts/corpus.js fetch` 会记录其哈希。

你无权再分发的文本，包括你自己的：

```bash
node scripts/corpus.js add-local my-2019-posts /path/to/file.md \
  --register blog --author "Name" --year 2019
```

文件留在原处。只有它的哈希、词数和元数据进入仓库，而 `fp-measure.js` 在它不存在的机器上会跳过它并附上一条说明。

最有价值的补充，正是本语料库目前缺失的那些：2010 年之后、处于人们真正会用本工具去检查的那些语域中的写作，并且有人愿意为其来源作担保。[误报上报表](https://github.com/conorbronsdon/avoid-ai-writing/issues/new?template=false_positive.yml)正是为接收这类内容而设的另一入口。
