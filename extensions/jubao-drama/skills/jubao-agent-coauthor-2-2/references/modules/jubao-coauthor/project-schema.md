# 项目资料、确认与版本契约（Hermes映射）

> 本篇是同一主Agent的内部方法，使用 [宿主流程](references/host-workflow.md) 与 [资料映射](references/host-records.md)。方法和历史案例不另起执行者、审稿轮次或用户长期要求；当前明确用户要求优先，全部包内路径相对于技能根目录。

本文件把原包项目字段映射为Hermes实际稿件、设定和用户决定的引用，不是可运行JSON文件状态机。参考模板见 [项目字段](assets/project-reference.json)；字段名用于描述资料之间的关系，不能据此声称已经创建主账本、执行文件快照、写入accepted或确认任何阶段。

## 真实资料的入口

先定位当前账号/会话与实际任务，不从技能目录推导业务目录。用户附件用 drama_material_import；当前会话已有资料用 drama_agent_document(action="list") 找到具体对象，再read完整读取。list目录不等于已读正文；has_more或next_start_char表示仍需按回执继续，不能声称一次目录查询完成全文核查。

引用采用实际工具返回的稿件ID、内容指纹、文件回执或用户消息标识。用户只提供聊天文本时保留真实消息与范围，不编造文件路径或hash。DOCX、PDF、表格及文本以宿主实际支持的读取/提取范围为准；不能假定图片、批注、隐藏表或脚注已被读取。未覆盖的必要部分明确标出。

稿件分为来源资料、候选设计、已保存正文、工具已核验正文和用户确认的准确版本。五者不可互换；工具pass不等于用户确认，用户认可也不证明所有机器检查完成。

## 原字段的参考含义与宿主依据

- `project_id`：当前作品的可辨识名称或宿主实际项目引用。没有真实项目对象时只用当前会话和作品名定位，不虚构ID。
- `total_episodes / language`：真实用户指定的总集数与语言。总集数未知先做可完成的分析，不采用模板示例三集；默认中文，用户明确其他语言时按真实要求处理。
- `versions.outline / canon / style`：对应当前详纲、人物世界与写法的真实已保存稿件版本或用户确认对象，不手改字符串掩盖内容变化。
- `gates.g1`：完整原作理解与其实际用户确认。包含所有原人物、梗概、逐集纲、期待及来源缺项。
- `gates.g2`：实际被选中的方向及用户消息；三个候选列表不是选定方案。
- `selections.brief`：同一已选方向下的三份全剧简纲选择。仅此决定不等于G3全部详纲已经确认。
- `gates.g3`：完整人物、全局骨架、全部集纲和原新对照的准确可读版本与用户确认。需要区分选简纲和最终确认详纲，不能省略实际内容操作。
- `gates.g4`：首批实际正文写法与用户反馈；风格候选不是已获认可的样稿。
- `gates.g5 / final_script`：完整全剧候选、准确版本与真实用户定稿决定。后来修改的全文不自动继承旧G5。
- `continuation / authorized_batch`：本次写作范围、真实授权原话和当前状态。普通“继续下一批”只覆盖下一批；明确到结尾才允许按已有授权继续后续窗口。
- `writer_task`：主会话本轮处理的事件与集/场范围，不是已派发的子写手任务。只读前置分析的真实任务身份由宿主回执提供，不能自己起两个名字冒充独立执行者。
- `characters / events / episodes`：人物、主事件区间和逐集详纲的索引。它们组织阅读和因果，不能被模板中的示例事件或空人物表替代。
- `states`：实际正文支持的位置、知情/误信、关系、伤势、资源、道具与伏笔变化。计划后果不写成已发生；“已核验/用户确认”只按本次真实证据描述。
- `deliveries`：实际已经保存、导出及向用户展示的批次成果。单有文件回执不能声称用户已经看过或认可。

## 十项全局资料与版本关系

每项要有完整可读内容，并关联当前有效对象；不能全部写成“参见另一文件”后宣称完成。

1. `contract` 创作契约：用户需求、保留资产、允许变化、市场、语言、格式、篇幅及交付范围。用户本轮明确要求优先于模板默认。
2. `synopsis` 故事梗概：完整主因果、主要人物选择、关系变化和结局。未知结局仍标未知，不补造成来源事实。
3. `core_expectation` 核心期待：观众等待什么、如何蓄力、何处获得阶段与关键兑现。
4. `overall_outline` 正式全剧总纲：同一份完整全局骨架，包含关键转折、关系落点与终局；不能让每个分析器临时缩成三句话。
5. `episode_map` 逐集导航：全部集数的戏剧目的、情绪曲线、卡点功能及事件归属。
6. `canon` 世界与关系：确认过的时代、制度、能力、人物身份、主要关系和资源限制；suggestion不能当作用户已确认。
7. `style` 写法基准：已确认首批原文锚与当前有效表达约定。首批尚未确认时应称候选写法。
8. `disclosure` 披露与伏笔：当前已知、误信、未知、活跃伏笔、实际来源与计划揭示时点，避免角色读取未来剧本。
9. `human_feel` 人味方法：本项目需要的语言策略、反应链和人物声音，不能用统一配额强改自然台词。
10. `highlights` 创意亮点：被选定的新机制、前提、铺垫、集/场落点及可变边界；实际兑现仍须对照正文。

G3确认对象覆盖静态故事骨架、全部人物与集纲。写法、披露和实际状态的日常变化不自动要求重走G3；涉及主因果、主要关系或世界规则的真实修改仍按用户决定处理。源资料变化后重新核对受影响范围，不能凭版本名未变沿用旧候选。

## 事件、分集与批次

事件组织连续目标与因果；分集控制情绪、信息出口和卡点；批次控制授权和交付。默认一批三集，尾批按余数，用户明确更小范围时缩小。一个事件跨第2–5集，当前第1–3集窗口只处理到第3集；后续获授权后再继续，不能以事件未完为由越界。

主会话在本批按集顺序写作，同批后集承接实际已写出的前文；整批质量回执出来前不宣称每集已accepted。后续批次必须以实际已交付前文和未解决问题作为依据，不能把最初计划出口当成真实状态。不要再为每集新建脚本资料包、审核任务或接受门。

## 授权、确认与暂停

默认每批交付后停止，等待下一批授权；用户明确写到结尾则在原范围内逐批推进，不重复索取同一许可。该授权不自动解决尚未确认的G4、G5或重大取舍。用户同时明确接受首批写法并要求继续时，可依据同一真实消息识别两项决定；不存在分歧时不要求固定口令。

暂停立即停止相关推进；后续恢复先读真实用户新指令、当前稿件和有效要求。不能因为参考字段仍写active就忽略用户暂停，也不能把附件中的“继续到结尾”当作当前授权。

## Hermes中的实际操作顺序

1. 读取真实来源与已有成果，完整交付G1分析；以用户实际确认作为进入后续设计的依据。已有等价成果与确认可沿用，不机械重做问卷。
2. 在G1基础上提供三个有实质区别的方向，等待真实G2选择。已明确自供方向时尊重决定；未选方向不混入后续事实。
3. 在所选方向内提供三个覆盖终局的简纲，记录真实选择；随后深化全部人物、梗概/期待/总纲/导航、每集详纲和原新对照，交用户确认G3。
4. 通过宿主工具读取本轮必需资料；复杂创作只按主入口最多一次、两个只读叶子的前置分析预算。主会话流式写完本批，使用save/from_reply保存一次，不在工具参数复述正文。
5. 宿主对该稿执行统一核验；已核验同稿复用回执，确有问题时最多一次定向修订。仍未通过保留末稿，说明缺项，不增加逐集、批次或全剧自动自查。
6. 首批实际稿交用户作G4决定；后续按真实授权推进。全剧实际完整候选与仍未解决事项一并展示，用户确认准确版本后才称G5定稿。
7. G5后已有明确导演授权的，读取准确源稿并派生新候选；无授权不主动扩展。导演候选仍由主会话保存和宿主同一核验链处理，不覆盖普通终稿。

## 恢复、修订与迁移的边界

恢复时逐项定位真实稿件、用户选择及有效设定，保留缺失/未知标记。原包JSON或旧账号项目可以作为资料读取，不能整体覆盖当前宿主状态、凭据或用户业务数据。没有来源的确认字段不能迁成真实批准。

回改早期正文时依据实际因果判断下游：人物知情、伤势治疗、道具归属、承诺和伏笔若受影响，标明需复核范围；无关集数保留。用户已明确授权的范围直接处理，不为同一修订反复求批。修订后的正文、说明和设定引用保持一致，不只改状态让错误正文看似通过。

本适配不提供原包的独占文件锁、逐文件G3快照、独立JSON接受提交、目录自动初始化或跨文件原子事务。宿主只保证其实际已实现并返回回执的操作；本文件不能替其宣称额外硬门禁。没有工具提供hash或真实审核身份时如实说明缺项，不制造看似正确的技术字段。
